# 次フェーズ仕様・設計

A（地区表の取り込み）は[requirements.md](requirements.md) 4.1節で初回設定の**主経路**と
定めたため、単なる次フェーズの改善項目ではなく、その主経路を実際に機能させるための
前提条件になっている。B（ローカル通知）はAとは独立に着手できる追加機能で、優先度はAより低い。

## A. 地区表の取り込み

### A.1 目的

収集曜日は利用者が決めるものではなく、住んでいる地区で市がすでに決めているものである。
「利用者が自分で収集曜日を登録する」方式（現行の`AreaEditorPage`の主UI）は、
地区表データ（`areas.json`の`areas`）を持たないための**暫定の代替手段**であり、
最終形ではない。町丁目から地区を選ぶだけで収集曜日が確定する状態を主経路にする。

### A.2 仕様

- 初回設定・地区変更画面の主UIを「地区から選ぶ」に置き換える
  - 区を選ぶ（既存の`saitamaWards`のChoiceChipをそのまま流用）
  - その区に属する地区（町丁目のグループ）の候補一覧から選ぶ。1区に複数パターンあるのが
    通常（例：西区には収集曜日パターンが3つある）。候補が多い区は町丁目名で絞り込めるようにする
  - 選ぶと区分ごとの収集曜日・早朝収集地区かどうかが確定した状態で反映される。反映後も
    これまでどおり曜日を個別に調整できる（市の地区表が誤っていた場合の逃げ道を残す）
- **郵便番号による絞り込み（検討中）**：郵便番号を入力すると区・地区の候補を絞り込む
  補助入力を提供できないか検討する。ただし今回の調査では、さいたま市の公式ツールが
  郵便番号入力に対応している形跡は見当たらなかった。また町丁目（＝収集区分の単位）と
  郵便番号は必ずしも1対1ではない（1つの郵便番号が複数の収集パターンにまたがる、
  あるいはその逆がありうる）ため、「郵便番号だけで1件に確定する」ことは保証できない。
  実装するとしても「候補を絞り込むショートカット」に位置づけ、複数候補が残れば
  A.2の一覧選択に合流させる。地区データ（A.4）が揃った段階で、郵便番号との対応が
  実際にどれくらい素直かを確認してから着手判断する
- 「自分の地区が見つからない」を選んだ場合のみ、区分ごとに曜日を手入力する画面
  （現行の`AreaEditorPage`の入力UI）に進む代替経路として残す
- 出典（市の収集日カレンダーの公開ページ）と、取り込んだデータの版（更新日）を
  設定画面の「このアプリについて」に表示する

### A.3 設計

データモデル・読み込み経路はすでに実装済みで、埋めるのは`assets/data/areas.json`の
`areas`配列だけで足りる（[design.md](design.md) 3章）。

```
AreaCatalog.areasInWard(ward)  実装済み・テスト済み（test/data/area_catalog_test.dart）
CollectionArea.fromJson         実装済み
```

`areas`の1件は`CollectionArea`のJSON表現そのもの（[requirements.md](requirements.md) 5.4の
`presets`と同じ形。`id`に町丁目由来の一意なIDを振る）。

追加が必要なのはUI側のみ：

```
AreaEditorPage
  区を選ぶ
   ├ 町丁目から選ぶ（新規） → 一覧 → CollectionArea を選択 → 各ドラフトに反映
   │                            （_applyPreset と同じ経路、対象がpresetsではなくareas）
   └ 自分で設定する（既存のフロー、変更なし）
```

`_applyPreset`は現状プリセット専用の名前になっているが、地区データを適用する処理と
実質同じ（`CollectionArea`を受けて`_drafts`に反映するだけ）なので、地区選択でも
そのまま再利用できる見込み。

### A.4 データ整備（アプリ外の作業・現状のボトルネック）

市の「収集日カレンダー」から町丁目→曜日の対応表を作る必要がある。このデータ整備は
アプリのコード変更を伴わないため、A.2/A.3の実装より先に着手できる。一方で、
このデータさえ揃えば主経路のUIは載せられる設計にしてあるため（A.3参照）、
**現状はここがA全体のボトルネックになっている。**

**調査状況（このドキュメント作成時点）**：さいたま市は地区を選ぶと収集曜日を確認できる
「収集日カレンダー」を公式に提供しており
（[requirements.md](requirements.md) 5.4節の`source`）、地区が収集曜日を一意に決めるという
このアプリの前提はここに基づく。ただしこのツールは区→地区の階層選択で動くJavaScript製の
ウィジェットで、静的なページ取得・PDF読み取りでは町丁目→曜日の対応データを機械的に
取得できなかった（画像ベースのPDFマニュアルには区分ごとの品目情報はあるが、
町丁目別の対応表そのものは含まれていなかった）。

**取りうる方法（優先度順）**：

1. **ヘッドレスブラウザでツールを操作して収集する**：`収集日カレンダー`の区→地区選択を
   自動操作し、各地区の曜日を機械的に読み取る。本リポジトリの環境には現時点で
   ブラウザ自動化ツール（Playwright等）が入っていないため、着手時に別途セットアップが要る
2. **手作業で転記する**：区ごとの町丁目数はそれほど多くない想定なので、区を1つずつ
   ツールで確認しながら`areas.json`に手で起こす。全10区を一度に揃える必要はなく、
   区ごとに段階的に投入してよい（未投入の区は「自分の地区が見つからない」の代替経路に
   自然にフォールバックする）
3. **市への問い合わせ**：データの二次利用可否も含め、環境局資源循環政策課
   （048-829-1338）に構造化データの提供有無を確認する余地がある

いずれの方法でも、`areas.json`の`areas`配列のスキーマに変換する部分は
`CollectionArea.fromJson`がそのまま使えるため、変換スクリプトは
`scripts/`配下に薄いものを1つ用意すれば足りる。

## B. 収集日前夜のローカル通知

### B.1 目的

ごみ出しは前夜に思い出す行動（[requirements.md](requirements.md) 1章）という設計方針の
延長線上として、アプリを開かなくても前夜に気づける手段を用意する。

### B.2 仕様

- 設定画面に通知のON/OFFスイッチと通知時刻を追加する（デフォルトOFF、時刻は20:00）
- 通知対象は「翌日に収集がある区分」。複数区分ある日は1通の通知にまとめる
  （例：「明日はもえるごみ・資源物1類の日です」）
- 年末年始の休止期間（1/1〜1/3の前夜）は通知しない
- 通知をタップするとアプリを開き、ホーム（明日のカード）を表示する
- 初回、通知をONにするタイミングでiOSの通知許可ダイアログを出す。拒否された場合は
  スイッチをOFFに戻し、設定アプリへの案内を表示する

### B.3 設計

- `flutter_local_notifications`を導入する（サーバー通信を持たない方針
  ([requirements.md](requirements.md) 6章)と矛盾しないローカル通知のみのパッケージ）
- スケジューリング方式：厳密な繰り返し通知（曜日指定の定期通知）ではなく、
  「地区のルールが変わったとき」と「アプリを開いたとき」に、その時点からの
  直近N日分（例：30日）を`CollectionCalendar.upcoming`で計算し、都度スケジュールし直す方式にする
  - 理由：`CollectionRule`の第◯曜日パターンはOS標準の「毎週◯曜」繰り返し通知だけでは
    表現できない（第2・第4のような月内の週指定があるため）。日付ごとに個別スケジュールする
    ほうが`CollectionCalendar`の判定ロジックをそのまま使い回せて二重実装にならない
  - 直近N日分を都度張り直すことで、地区設定を変更したときに古い通知が残る問題も解消する
- 通知権限・スケジュール操作をラップする`NotificationRepository`を`lib/data/`に追加し、
  `SettingsRepository`と同様に`providers.dart`から購読する設計にする（既存の
  data層→providers層の構造をそのまま踏襲）
- 通知ON/OFFと時刻も`SettingsRepository`が保存する対象に加える
  （`CollectionArea`とは別キーにする。地区を変更しても通知設定は保持されるべきため）

### B.4 テスト方針

`flutter_local_notifications`のOS連携部分はウィジェットテストで検証できないため、
「地区のルールから通知すべき日付・区分の集合を計算する」ロジックを`CollectionCalendar`を
使った純粋関数として`lib/domain/`側に切り出し、そこだけを単体テストで担保する
（OS API呼び出し自体はテスト対象にしない）。

## C. スコープ外のまま据え置くもの

粗大ごみの受付可否判定・「これは出せるか」をAIに聞く機能は、A・Bより前提となる情報
（品目ごとの判定基準、市への申込導線）の整理が別途必要なため、本ドキュメントでは
仕様化しない。着手する場合は先に別ドキュメントとして要件を切り出す。
