# 次フェーズ仕様・設計

現状（[requirements.md](requirements.md) 7章のスコープ外）に挙がっている項目のうち、
着手が具体的に見えている2つを扱う。実装順もこの並び。

## A. 地区表の取り込み

### A.1 目的

現在は「利用者が自分で収集曜日を登録する」方式（[requirements.md](requirements.md) 4.1）だが、
これは地区表データを持たないための代替手段であって最終形ではない。町丁目を選ぶだけで
収集曜日が確定すれば入力の手間と入力ミスの両方が減る。

### A.2 仕様

- 初回設定・地区変更画面に「町丁目から選ぶ」導線を追加する
  - 区を選ぶ（既存の`saitamaWards`のChoiceChipをそのまま流用）
  - その区に属する町丁目（地区）の一覧から選ぶ
  - 選ぶと区分ごとの収集曜日が確定した状態で反映される。反映後もこれまでどおり
    曜日を個別に調整できる（市の地区表が誤っていた場合の逃げ道を残す）
- 「自分で設定する」（現行フロー）は町丁目データが見つからない・分からない場合の
  代替として残す
- 出典（市の収集日カレンダーの公開ページ）と、取り込んだデータの版（更新日）を
  設定画面の「このアプリについて」に表示する

### A.3 設計

データモデル・読み込み経路はすでに実装済みで、埋めるのは`assets/data/areas.json`の
`areas`配列だけで足りる（[design.md](design.md) 3章）。

```
AreaCatalog.areasInWard(ward)  実装済み・テスト済み（test/data/area_catalog_test.dart）
CollectionArea.fromJson         実装済み
```

`areas`の1件は`CollectionArea`のJSON表現そのもの（[requirements.md](requirements.md) 5.4の
`presets`と同じ形。`id`に町丁目由来の一意なIDを振る）。

追加が必要なのはUI側のみ：

```
AreaEditorPage
  区を選ぶ
   ├ 町丁目から選ぶ（新規） → 一覧 → CollectionArea を選択 → 各ドラフトに反映
   │                            （_applyPreset と同じ経路、対象がpresetsではなくareas）
   └ 自分で設定する（既存のフロー、変更なし）
```

`_applyPreset`は現状プリセット専用の名前になっているが、地区データを適用する処理と
実質同じ（`CollectionArea`を受けて`_drafts`に反映するだけ）なので、地区選択でも
そのまま再利用できる見込み。

### A.4 データ整備（アプリ外の作業）

市の「収集日カレンダー」から町丁目→曜日の対応表を作る必要がある。案：

1. 市公開のPDF/ページから町丁目・区分・曜日の対応を書き出す（手作業 or スクレイピング）
2. `areas.json`の`areas`配列のスキーマに変換するスクリプトを`scripts/`配下に用意する
3. 区ごとに段階的に投入する（全10区を一度に揃える必要はない。空の区は「自分で設定する」に
   自然にフォールバックする）

このデータ整備はアプリのコード変更を伴わないため、A.2/A.3の実装より先に着手できる。

## B. 収集日前夜のローカル通知

### B.1 目的

ごみ出しは前夜に思い出す行動（[requirements.md](requirements.md) 1章）という設計方針の
延長線上として、アプリを開かなくても前夜に気づける手段を用意する。

### B.2 仕様

- 設定画面に通知のON/OFFスイッチと通知時刻を追加する（デフォルトOFF、時刻は20:00）
- 通知対象は「翌日に収集がある区分」。複数区分ある日は1通の通知にまとめる
  （例：「明日はもえるごみ・資源物1類の日です」）
- 年末年始の休止期間（1/1〜1/3の前夜）は通知しない
- 通知をタップするとアプリを開き、ホーム（明日のカード）を表示する
- 初回、通知をONにするタイミングでiOSの通知許可ダイアログを出す。拒否された場合は
  スイッチをOFFに戻し、設定アプリへの案内を表示する

### B.3 設計

- `flutter_local_notifications`を導入する（サーバー通信を持たない方針
  ([requirements.md](requirements.md) 6章)と矛盾しないローカル通知のみのパッケージ）
- スケジューリング方式：厳密な繰り返し通知（曜日指定の定期通知）ではなく、
  「地区のルールが変わったとき」と「アプリを開いたとき」に、その時点からの
  直近N日分（例：30日）を`CollectionCalendar.upcoming`で計算し、都度スケジュールし直す方式にする
  - 理由：`CollectionRule`の第◯曜日パターンはOS標準の「毎週◯曜」繰り返し通知だけでは
    表現できない（第2・第4のような月内の週指定があるため）。日付ごとに個別スケジュールする
    ほうが`CollectionCalendar`の判定ロジックをそのまま使い回せて二重実装にならない
  - 直近N日分を都度張り直すことで、地区設定を変更したときに古い通知が残る問題も解消する
- 通知権限・スケジュール操作をラップする`NotificationRepository`を`lib/data/`に追加し、
  `SettingsRepository`と同様に`providers.dart`から購読する設計にする（既存の
  data層→providers層の構造をそのまま踏襲）
- 通知ON/OFFと時刻も`SettingsRepository`が保存する対象に加える
  （`CollectionArea`とは別キーにする。地区を変更しても通知設定は保持されるべきため）

### B.4 テスト方針

`flutter_local_notifications`のOS連携部分はウィジェットテストで検証できないため、
「地区のルールから通知すべき日付・区分の集合を計算する」ロジックを`CollectionCalendar`を
使った純粋関数として`lib/domain/`側に切り出し、そこだけを単体テストで担保する
（OS API呼び出し自体はテスト対象にしない）。

## C. スコープ外のまま据え置くもの

粗大ごみの受付可否判定・「これは出せるか」をAIに聞く機能は、A・Bより前提となる情報
（品目ごとの判定基準、市への申込導線）の整理が別途必要なため、本ドキュメントでは
仕様化しない。着手する場合は先に別ドキュメントとして要件を切り出す。
